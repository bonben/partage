2. TP 2 : lire, casser et modifier un driver¶

Durée : 1 h. Objectif : savoir lire un driver, le relier au device tree, et diagnostiquer quand il ne s'attache pas. Le driver est fourni : on le lit et on le modifie, on ne l'écrit pas. Les parties 2.1 à 2.4 sont pour tous ; la 2.5 est pour les rapides, puis montrée par le formateur en fin de séance.

Deux drivers sont fournis dans tp2 :

Fichier Nature Adresse de l'IP
chenillard.c driver de caractère simple écrite dans le code
axi_btns.c driver de plateforme des boutons, avec lecture bloquante réveillée par l'interruption lue dans le device tree, comme l'interruption

2.1 Lire le driver du chenillard¶

Dans VS Code (ouvert au TP 1, sinon code /srv/nfsroot/arkane/home/user/tp sur le poste), ouvrez tp2/chenillard.c. Lisez chenillard_init, chenillard_i_read et chenillard_i_write.

Trois appels font l'essentiel de chenillard_init (transparent « Trois appels à reconnaître dans un driver ») :

Appel Ce qu'il fait
register_chrdev inscrit le driver sous un numéro majeur : tout fichier de /dev qui porte ce numéro mène à ses fonctions read et write
request_mem_region réserve la plage d'adresses physiques des registres
ioremap rend une adresse du noyau qui mène à ces registres

Questions

  • Quelle est la différence entre l'adresse donnée à ioremap et celle qu'il rend ? À quel appel du TP 1 ressemble-t-il ?
  • D'où vient l'adresse du chenillard dans ce driver ? Qu'est-ce que cela rappelle du TP 1 ?
  • Que fait ce driver que /dev/mem ne faisait pas ?

2.2 Compiler et charger¶

Sur le poste
cd /srv/nfsroot/arkane/home/user/tp/tp2
make
Sur la carte
cd /home/user/tp/tp2
./load.sh

Une erreur au chargement ? C'est prévu

./load.sh affiche une erreur de mknod pour /dev/btns. C'est normal : le driver des boutons a une panne volontaire, qu'on traite en 2.3. Pour l'instant, on ne s'occupe que du chenillard, qui lui doit fonctionner.

Regardez maintenant, une commande à la fois, ce que le chargement du driver du chenillard a changé :

Sur la carte
dmesg | tail

Les derniers messages du noyau. Cherchez les deux lignes qui commencent par chenillard: : le driver annonce son chargement, puis son numéro majeur et l'adresse de ses registres. La ligne loading out-of-tree module taints kernel est un avertissement sans conséquence : il signale un module qui ne fait pas partie du noyau.

Sur la carte
cat /proc/devices

La table des drivers de caractère inscrits, avec leur numéro majeur. Cherchez chenillard, et regardez qui d'autre est là.

Sur la carte
cat /proc/iomem

La carte des adresses physiques réservées. Cherchez chenillard, absent au TP 1.

Sur la carte
ls -l /dev/chenillard

Le fichier spécial, avec ses deux numéros (majeur, mineur) à la place de la taille.

Questions

  • Le numéro affiché par /proc/devices : où le retrouve-t-on dans dmesg et dans ls -l /dev/chenillard ?
  • Quel appel du driver a fait apparaître la ligne chenillard dans /proc/iomem ? Elle n'y était pas au TP 1.

Le chenillard se pilote maintenant depuis le shell, en écrivant trois octets : mode, vitesse, motif.

Sur la carte
printf '\001\007\000' > /dev/chenillard

2.3 Une panne¶

Le chargement des modules s'est bien passé, et pourtant /dev/btns ne fonctionne pas. Trouvez pourquoi, sans lire le code d'abord : où le noyau devrait-il montrer que le driver des boutons a trouvé son périphérique ?

Sur la carte
ls /sys/bus/platform/devices/
ls /sys/bus/platform/drivers/axi_btns/
cat /proc/device-tree/amba_pl/gpio@41200000/compatible ; echo
cat /proc/interrupts

Une fois la cause trouvée : corrigez, recompilez, puis rechargez.

Sur le poste
make
Sur la carte
./unload.sh
./load.sh
dmesg | tail

dmesg doit maintenant afficher l'interruption lue dans le device tree.

Questions

  • Quelle fonction du driver le noyau appelle-t-il quand il trouve un nœud qui correspond ?
  • Que se serait-il passé si l'erreur avait été dans le device tree plutôt que dans le driver ?

2.4 Une modification¶

Sur la carte
cat /dev/chenillard
hexdump -C /dev/chenillard
./app

cat et hexdump n'affichent rien, alors que le programme app lit bien l'état du chenillard. Lisez chenillard_i_read et trouvez pourquoi (man 2 read : que signifie une valeur de retour nulle ?).

Corrigez le driver pour que hexdump affiche les trois octets une fois, puis s'arrête.

La fonction à modifier fait dix lignes, et la correction en ajoute trois.

Indice 1

read doit rendre le nombre d'octets copiés. Rendre 0 signifie « fin de fichier » : cat s'arrête sans rien afficher. Et si l'on rend toujours 3, cat relit sans fin : il faut se souvenir que tout a déjà été lu. C'est le rôle de *f_pos, la position dans le fichier.

Indice 2 : la structure 
if (*f_pos >= 3)
    return 0;            /* tout a déjà été lu : fin de fichier */
/* ... lecture des trois registres et copy_to_user, inchangés ... */
*f_pos += 3;
return 3;

Recompilez (make sur le poste), puis ./unload.sh et ./load.sh sur la carte.

2.5 Pour les rapides : interruption et lecture bloquante¶

Sur la carte
cat /proc/interrupts | grep btns    # noter le compteur
./app                               # appuyer sur les boutons, Ctrl-C pour sortir
cat /proc/interrupts | grep btns

Questions

  • Pendant que app attend un bouton, combien de CPU consomme-t-il ? Comparez avec le programme qui scrutait les interrupteurs au TP 1.
  • Dans axi_btns.c, que fait la routine d'interruption, et pourquoi écrit-elle dans le registre ISR ?

2.6 Pour aller plus loin¶

  • thread_app : boutons et clavier en même temps, avec deux threads.
  • Comparez axi_btns_of_probe avec la fonction probe donnée en annexe des transparents : platform_get_resource et request_irq contre devm_platform_ioremap_resource et devm_request_irq. Qu'apportent les fonctions devm_ ?
  • Faites du chenillard un driver de plateforme, sur le modèle des boutons : son nœud compatible = "imt,chenillard" existe déjà dans le device tree.
